## Schritt 2: Einmaliges Lesen *(IHK-relevanter Text, phänomenologisch aufbereitet)*

### 1. Warum Unit-Tests „Banana Ware“ verhindern
Wenn Projekttermine brennen, wird am ehesten am Testen gespart. Das Ergebnis nennt man spöttisch **„Banana Ware“** – Software, die „grün“ ausgeliefert wird und erst bei der Kundschaft reift. Manuelles Durchklicken nach jeder Codeänderung ist zu langsam und vergisst regelmäßig Randfälle. Die Erkenntnis der Softwaretechnik lautet daher: **Code prüft Code am exaktesten.**

Auf kleinster Ebene geschieht das durch **Unit-Tests (Klassentests)**: Sie testen einzelne Funktionen oder Klassen isoliert, schnell und wiederholbar (darüber liegen *Integrationstests* für das Zusammenspiel und *End-to-End-Tests*, z. B. mit Selenium). Fast jede Sprache besitzt ein **xUnit-Framework** – in Python etwa `unittest`/`pytest`, in Java der Klassiker **JUnit 5** (von Erich Gamma & Kent Beck; bestehend aus *Platform*, *Jupiter* und *Vintage*).

In Maven-/Java-Projekten spiegelt der Testordner exakt den Quellcodepfad: Produktionscode liegt unter `src/main/.../Article.java`, der zugehörige Test parallel unter `src/test/.../ArticleTest.java`. Jede Testmethode trägt `@Test`, beginnt konventionell mit `test...` und prüft mit Assertions wie **`assertEquals(erwartet, istwert)`** automatisch das Ergebnis. Beim Testlauf (`mvn test`) unterscheidet die Auswertung sauber zwischen:
- **Failure:** Eine `assert*()`-Zusicherung schlug fehl (die Fachlogik stimmt nicht).
- **Error:** Es trat eine unerwartete Laufzeit-Exception auf (Programmabsturz).

### 2. Testgetriebene Entwicklung (TDD): Red – Green – Refactor
Damit Tests unter Zeitdruck niemals „auf später“ verschoben werden, dreht **Test-driven Development (TDD / Test-first)** die Reihenfolge komplett um: Du schreibst **zuerst den Test**, und **erst danach den Produktivcode**. Dieser enge Takt heißt **Red – Green – Refactor**:
1. **Red:** Du formulierst eine konkrete Erwartung als `@Test` (inkl. Minimal-Dummy, damit es kompiliert) und startest den Testlauf. Er **muss** rot fehlschlagen (`BUILD FAILURE`) – so beweist du, dass der Test wirklich prüft.
2. **Green:** Du schreibst den einfachsten möglichen Code, damit der Test grün wird (`BUILD SUCCESS`).
3. **Refactor:** Jetzt räumst du den Code auf (Doppelungen entfernen, Logik verallgemeinern, Namen klären) – und lässt sofort **alle Tests erneut laufen**, um sicherzugehen, dass nichts kaputtgegangen ist.

Kent Beck vergleicht TDD mit einer gezahnten Brunnenkurbel: Jeder grüne Test rastet sicher ein, sodass das Projekt jederzeit *„clean code that works“* bleibt.

### 3. Qualitätssicherung & die drei Dokumentationsarten
Unit-Tests (typisch **Whitebox-Tests** mit Codekenntnis) werden ergänzt durch **Blackbox-Tests** (Prüfung gegen Spezifikation ohne Codeblick) und **Code-Reviews** im Team. Abgeschlossen wird jede professionelle Softwarelieferung durch drei klar getrennte **Dokumentationen** für unterschiedliche Zielgruppen:
- **Entwicklerdokumentation:** Architektur, Klassen, Schnittstellen und Docstrings/Javadoc/pydoc für Wartung und Weiterentwicklung.
- **Betriebsdokumentation:** Installation, Konfiguration, Ports, Logs, Rechte und Backups für Admins im Betrieb.
- **Benutzerdokumentation:** Verständliche Handbücher, Tutorials und FAQs für die Endanwender.
