## 📖 Schritt 2: Einmaliges Lesen *(Fokus-Wissen aus Kersken)*

### 1. Systemintegration statt Medienbrüche *(Kersken 19.2.1–19.2.2)*

Medienbrüche (Daten aus System A manuell abtippen oder per CSV-Mail in System B laden) sind die Hauptquelle für Fehler und Liegezeiten. Moderne Prozessautomatisierung verbindet Systeme direkt über **REST-APIs** (HTTP + JSON) und Python-Skripte.

| HTTP-Methode | CRUD-Aktion | Beispiel im Geschäftsprozess |
| :--- | :--- | :--- |
| **`GET`** | Read *(Lesen)* | Offene Bestellungen aus Shop-API abrufen |
| **`POST`** | Create *(Anlegen)* | Neuen Kunden oder Rechnung im ERP anlegen |
| **`PUT` / `PATCH`** | Update *(Ersetzen / Teiländern)* | Bestellstatus auf `"versendet"` setzen |
| **`DELETE`** | Delete *(Löschen)* | Temporären Import-Job entfernen |

| HTTP-Statuscode | Bedeutung | Reaktion im Automatisierungs-Skript |
| :--- | :--- | :--- |
| **`200 OK` / `201 Created`** | Erfolg / Ressource angelegt | JSON-Antwort parsen und weiterverarbeiten |
| **`400 Bad Request` / `401` / `403`** | Client-Fehler / Auth fehlgeschlagen | **Nicht** blind wiederholen → Fehler loggen & Alert senden |
| **`404 Not Found`** | Ressource existiert nicht | Fachliche Ausnahmebehandlung |
| **`429` / `500` / `503`** | Rate-Limit oder Serverfehler | **Exponential Backoff / Retry** nach Wartezeit |

> [!question] ⏸️ Denkstopp (10 Sek.)
> Warum ist es gefährlich, bei einem `400 Bad Request` (ungültige JSON-Daten) eine automatische Endlos-Retry-Schleife zu programmieren?

### 2. Robuste Python-Automation *(7.1.4 + Praxis)*

```python
import requests

url = "https://api.erp.local/v1/orders"
headers = {"Authorization": "Bearer <TOKEN>", "Accept": "application/json"}

resp = requests.get(url, headers=headers, timeout=10)
resp.raise_for_status()                 # Wirft Exception bei 4xx / 5xx!
orders = resp.json()                    # Parst JSON direkt in Python-Dict/List
```

* **Best Practices für produktive Prozesse:**
  1. **Immer `timeout=...` setzen** (sonst hängt ein Cronjob/Worker ewig!).
  2. **Keine Secrets im Code** → API-Keys über Umgebungsvariablen (`os.environ`) laden.
  3. **Idempotenz & Logging:** Jeder Lauf protokolliert Erfolg/Fehler mit Zeitstempel; wiederholte Ausführung darf keine doppelten Buchungen auslösen.

## 🔺 Schritt 3: N – Nuklei & Pyramidenschema®

![[../../assets/LF11.07_Pyramide.svg]]

- **Spitze:** Python und REST-APIs (HTTP + JSON) eliminieren Medienbrüche durch automatisierte, fehlertolerante System-zu-System-Integrationen.
- **Nukleus 1 (REST & HTTP-Grundlagen):** GET (Read), POST (Create), PUT/PATCH (Update), DELETE Datenformat: JSON (UTF-8) Auth: Bearer Token / API-Key Statuscodes: 2xx OK, 4xx Clientfehler, 5xx Server
- **Nukleus 2 (Python-Integration):** requests.get/post(..., timeout=10) resp.raise_for_status() für saubere Fehlererkennung resp.json() → Dict / List Automatisierte ETL- & Webhook-Pipelines
- **Nukleus 3 (Produktions-Reife):** Timeouts sind Pflicht! Secrets via Env-Variablen (nie im Git-Repo!) Retry nur bei 429/5xx Logging & Idempotenz gegen doppelte Buchungen

> [!tip] 💡 IHK-Prüfungstipp
> Wenn in IHK-Aufgaben nach dem Nutzen einer API-Anbindung gefragt wird, nenne immer: **Vermeidung von Medienbrüchen**, **Echtzeit-Datenabgleich**, **Reduktion manueller Tippfehler** und **geringere Durchlaufzeiten**.
