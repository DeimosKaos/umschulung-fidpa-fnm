## Schritt 2: Einmaliges Lesen *(IHK-relevanter Text, phänomenologisch aufbereitet)*

### 1. Serverseitige Ausführung & Superglobals (Kersken 19.1)
**PHP (*PHP: Hypertext Preprocessor*)** läuft **ausschließlich auf dem Webserver** (z. B. Apache). Der Server führt `<?php ... ?>` aus, fragt ggf. MySQL ab und sendet nur das fertige Ergebnis (HTML oder JSON) an den Browser.
- **Eingabedaten:** Formulardaten landen in assoziativen Arrays (**Superglobals**): **`$_GET`** (URL-Parameter) und **`$_POST`** (Body).
- **Sessions (`$_SESSION`):** Da HTTP zustandslos ist (`LF 9.05`), merkt sich der Server Logins über `session_start()` und eine zufällige **Session-ID** (meist als Cookie).
- **XSS-Abwehr (*Cross-Site Scripting*):** Jede Benutzerausgabe im HTML **muss** mit **`htmlspecialchars($text, ENT_QUOTES, 'UTF-8')`** maskiert werden, damit `<script>`-Tags nicht im Browser ausgeführt werden!

> [!question] ⏸️ Denkstopp (10 Sek.)
> *Warum nützt es einem Angreifer nichts, im Browser „Seitenquelltext anzeigen“ zu drücken, um dein PHP-Datenbankpasswort auszulesen?*

### 2. MySQL-Anbindung & SQL-Injection-Schutz (`19.1.5`)
Beim Datenbankzugriff via **`mysqli`** oder **`PDO`** ist direkte String-Verkettung (`"SELECT * FROM users WHERE id=" . $_GET['id']`) fatal (**SQL-Injection**, vgl. Kersken `21.2.1`).
- **Die saubere Lösung – Prepared Statements:**
  ```php
  $stmt = $mysqli->prepare("SELECT name, price FROM articles WHERE id = ?");
  $stmt->bind_param("i", $id); // "i" = integer, "s" = string
  $stmt->execute();
  ```
  SQL-Befehl und Parameter werden **getrennt** an MySQL gesendet – eingeschleuste `' OR 1=1--`-Strings werden niemals als SQL-Code ausgeführt!
- **Passwörter:** Niemals im Klartext oder mit veraltetem MD5 speichern, sondern mit **`password_hash()`** und `password_verify()`.

> [!question] ⏸️ Denkstopp (10 Sek.)
> *Worin unterscheidet sich ein **Prepared Statement** technisch von `real_escape_string()` – warum gilt es als noch sicherer?*
