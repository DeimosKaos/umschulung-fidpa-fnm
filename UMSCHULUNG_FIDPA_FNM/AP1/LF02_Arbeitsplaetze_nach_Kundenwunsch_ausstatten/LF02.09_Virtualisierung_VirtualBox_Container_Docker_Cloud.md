## Schritt 2 – Einmaliges Lesen: Das Phänomen verstehen

### 1. Das Grundproblem: Leerlauf auf teurer Hardware
Wer die CPU- und Speicherauslastung normaler Computer beobachtet, sieht meistens sehr niedrige Prozentwerte – außer kurz beim Starten von Programmen. Gleichzeitig braucht ein Unternehmen aber getrennte Systeme: einen Webserver, eine Datenbank, vielleicht ein Testsystem unter Linux auf einem Windows-Rechner. Für jeden Dienst einen eigenen physischen Rechner zu kaufen, wäre Geld- und Stromverschwendung.

Die Lösung lautet **Virtualisierung**: Eine Software – der sogenannte **Hypervisor** (VM-Manager) – gaukelt einem **Gastbetriebssystem** vor, es laufe auf einem eigenen, unabhängigen Computer, obwohl es in Wahrheit auf der Hardware eines **Wirts- oder Hostbetriebssystems** ausgeführt wird.

### 2. Vollständige Virtuelle Maschinen (VMs) & VirtualBox
Bei einer klassischen VM wird ein kompletter Computer emuliert oder der Hardwarezugriff durch einen Hypervisor koordiniert:
- **Wichtige Lösungen:** **VMware** (Workstation, Server, ESX Server), **Xen** (Linux-Open-Source: *Domäne 0* bootet den Xen-Hypervisor und teilt den *Domänen* abwechselnd reale Hardwarezeit zu, ähnlich einem Prozess-Scheduler), **Microsoft Hyper-V**, **Parallels Desktop** (macOS, kann auch Boot-Camp-Partitionen booten) sowie **Oracle VirtualBox** (kostenlos, Open Source, für Windows, macOS, Linux, Solaris; ab Version 7 experimentell für Apple M1/M2 – wichtig: Das Gastsystem muss zur CPU-Architektur passen, z. B. ARM).
- **Vagrant** hilft dabei, komplette VM-Konfigurationen samt Betriebssystem und Software in einem Ruby-basierten *Vagrant-File* zu speichern und auf andere Rechner oder VM-Manager zu übertragen.

#### Worked Example: Eine VM in VirtualBox sauber aufsetzen & betreiben
1. **Name, Typ & RAM festlegen:** Typ/Version wählen und nur so viel RAM zuteilen, wie neben dem Host und eventuellen weiteren VMs frei ist.
2. **Virtuelle Festplatte anlegen:** Die Festplatte der VM ist auf dem Host normalerweise nur eine einzige Datei. Du wählst:
   - **Dateityp:** `VDI` (VirtualBox-Standard), `VHD` (Microsoft) oder `VMDK` (VMware – praktisch für Austausch zwischen VM-Managern).
   - **Speicherart:** *Feste Größe* (sofort voller Platz belegt, etwas bessere Performance) vs. *dynamisch alloziert* (wächst nur mit dem echten Bedarf).
3. **OS installieren:** Ein **ISO-Image** als virtuelles optisches Laufwerk einhängen (`Massenspeicher → Sekundärer Master`), VM starten und installieren. Eine Formatierung innerhalb der VM betrifft nur die virtuelle Festplattendatei!
4. **Bedienung optimieren:** Ohne *Mouse Capturing* befreit die Host-Taste (Standard: linke `Strg` bzw. `Cmd`) den Mauszeiger. Nach der Installation bindet man die **VirtualBox Guest Additions** ein (`Devices → Insert Guest Additions CD Image`) – sie liefern Treiber und aktivieren **Shared Folders**, **Shared Clipboard** und **Drag and Drop**.
5. **Sicher experimentieren & beenden:** Mit **Snapshots** (`Machine → Take Snapshot`) frierst du Speicher- und Festplattenstand ein, um Tests jederzeit rückgängig zu machen. Beim Schließen des Fensters hast du drei Modi: *Save the machine state* (RAM-Zustand sichern, Standard), *Send the shutdown signal* (sauber herunterfahren) oder *Power off the machine* (hartes Ausschalten wie Steckerziehen).

### 3. Container-Virtualisierung mit Docker: Warum weniger oft schneller ist
Eine VM schleppt für jede einzelne Anwendung ein komplettes eigenes Betriebssystem mit – das kostet viel RAM, Festplatte und Startzeit. Oft will man aber gar kein anderes Betriebssystem, sondern nur **abgeschlossene Anwendungsumgebungen**, die sich nicht gegenseitig stören.

Genau das machen **Softwarecontainer** (Weiterentwicklung des Prinzips von `chroot`, das nur die Dateisystemwurzel isoliert): Container isolieren Prozess-, System- und Netzwerkressourcen, **teilen sich aber den Kernel des Hostbetriebssystems** (auf Windows/macOS läuft dazu unter der Haube eine minimale Linux-VM). Der Nachteil: Man kann das OS im Container nicht völlig frei wie in einer VM wählen. Der riesige Vorteil: Container starten in Sekunden und verbrauchen viel weniger Ressourcen.

In der Praxis nutzt man **Docker** unter anderem für:
- vorgefertigte Serverdienste (Webserver, Datenbanken) aus öffentlichen Repositorys,
- identische Testumgebungen für Entwicklerteams,
- automatisierte Build-Pipelines (z. B. mit **Jenkins**), die getestete Apps direkt als Container für Server oder Cloud (AWS/Azure) verpacken.

#### Worked Example: MySQL als Docker-Container produktiv starten
1. Test & Suche: `docker run hello-world` prüft den Zugriff auf das Repository; `docker search mysql` sucht Images.
2. Start mit den vier wichtigsten Optionen:
   ```bash
   docker run --name mysql-test \
     -p 3307:3306 \
     -v ~/databases:/var/lib/mysql \
     -e MYSQL_ROOT_PASSWORD=geheim \
     --restart unless-stopped \
     -d mysql:8.0
   ```
   - `-p 3307:3306`: leitet Host-Port `3307` auf Container-Port `3306` weiter (praktisch, wenn lokal schon ein MySQL auf `3306` läuft).
   - `-v ~/databases:/var/lib/mysql`: verbindet ein lokales Verzeichnis mit dem Container – sonst wären alle Datenbanken beim Entfernen des Containers weg!
   - `--restart`: `no` (Standard), `on-failure`, `always` oder `unless-stopped` (für Produktivbetrieb meist am sinnvollsten, da er nach Host-Reboot startet, aber manuellen Stopp respektiert).
   - `-d` (*detach*): startet im Hintergrund, blockiert das Terminal nicht.
3. Verwaltung: `docker ps` zeigt laufende Container samt kurzer Hex-ID; `docker exec -it <ID> /bin/bash` öffnet eine interaktive Shell im Container.
4. Automatisierung & Skalierung: Statt langer CLI-Befehle beschreibt ein **Dockerfile** den Aufbau. Für professionelle Cluster (automatisches Deployment, Nameserver-Einträge, verteilter Storage) nutzt man **Container-Orchestrierung**, vor allem **Kubernetes**.

### 4. Cloud Computing: Mieten statt selbst betreiben
Wer gar keine eigene Serverhardware mehr pflegen will, mietet Rechenleistung, Speicher oder Software dynamisch (oft stündlich) über das Internet:
- **IaaS (Infrastructure as a Service):** Du mietest virtualisierte Hardware inkl. wählbarem Betriebssystem (Linux/Windows), z. B. **Amazon AWS EC2** oder **Microsoft Azure**. (*Sonderform:* **Bare Metal Cloud** vermietet echte dedizierte Server stundenweise statt VMs.)
- **PaaS (Platform as a Service):** Du mietest gezielt fertige Plattformdienste wie Datenbanken, Streaming-Server oder Objektspeicher (z. B. **AWS S3**).
- **SaaS (Software as a Service):** Du mietest fertige Anwendungssoftware flexibel statt teurer Einzellizenzen – Updates sind inklusive.
- **Managed Service** (z. B. Rackspace gegen Aufpreis): Der Anbieter übernimmt zusätzlich die Administration.

**Professioneller Cloud-Betrieb:** Enterprise-Clouds lassen sich komplett über **REST-APIs** und **SDKs** (Java, Python, PHP, C#) steuern – Server werden per Code hochgefahren, Daten im Cloud-Storage abgelegt. Anbieter garantieren meist **99 bis 100 % Uptime** pro Jahr (bei Ausfall gibt es Gutschriften). **Wichtig für die Praxis:** Auch Cloud-Dienste können ausfallen (wie 2011 bei Amazon S3) – deshalb bleiben **lokale Backups** unverzichtbar!
