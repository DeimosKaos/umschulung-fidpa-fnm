## Schritt 2: Einmaliges Lesen *(IHK-relevanter Text, phänomenologisch aufbereitet)*

### 1. HTTP/1.1 & HTTP/2 im Überblick (Kersken 14.1)
**HTTP (*Hypertext Transfer Protocol*)** ist ein zustandsloses, klartextbasiertes **Request-Response-Protokoll** auf TCP-Port **80** (unverschlüsselt) bzw. **443** (HTTPS). **HTTP/2** (RFC 7540) ergänzt paralleles Multiplexing, Streaming und Header-Komprimierung bei gleicher Semantik.

**Ablauf einer Kommunikation (`14.1.1`):**
1. Browser zerlegt URL → DNS-Auflösung → TCP-Verbindung (Port 80/443).
2. **HTTP-Request:** Startzeile (`GET /pfad/index.html HTTP/1.1`), gefolgt von **Headern** (`Host: www.example.com` – *seit HTTP/1.1 Pflicht für virtuelle Hosts!*, `Accept`, `User-Agent`, `Connection: Keep-Alive`), Leerzeile und optionalem Body.
3. **HTTP-Response:** Statuszeile (`HTTP/1.1 200 OK`), Antwort-Header (`Content-Type` = MIME-Type z. B. `text/html`, `Content-Length`, `Last-Modified`, `ETag`), Leerzeile und Body (HTML/JSON/Bild).

### 2. HTTP-Methoden & Statuscodes (Kersken 14.1.1–14.1.2)
- **Methoden:**
  - `GET`: Ressource anfordern; Parameter stehen als **Query-String** in der URL (`?feld1=wert1&feld2=wert2`).
  - `POST`: Daten/Uploads im **Request-Body** senden (nicht in der URL sichtbar, für große Datenmengen & Formulare).
  - `HEAD`: Nur Header anfordern (z. B. Cache-Prüfung über `Last-Modified`/`ETag`).
  - `PUT` / `DELETE`: Ressource ändern/speichern bzw. löschen (wichtig für REST-APIs).
- **Statuscode-Klassen:**
  - `1xx` (*Informationen*): z. B. `100 Continue`.
  - `2xx` (*Erfolg*): z. B. `200 OK`, `201 Created`.
  - `3xx` (*Umleitung*): `301 Moved Permanently`, `302 Found`, `304 Not Modified` (aus Browser-Cache laden).
  - `4xx` (*Clientfehler*): **`401 Unauthorized`** (Login erwartet), **`403 Forbidden`** (Zugriff grundsätzlich verboten, auch mit Login), **`404 Not Found`** (URL/Ressource existiert nicht).
  - `5xx` (*Serverfehler*): **`500 Internal Server Error`** (Fehler im Server-Skript/Backend → Error-Log prüfen!).

### 3. Unix Meta-Server: `inetd` und `xinetd` (Kersken 15.2)
Selten genutzte Netzwerkdienste verbrauchen unnötig RAM, wenn ihr Daemon ständig im Hintergrund läuft. Ein **Meta-Server** (*Superserver* wie `inetd` oder das sicherere **`xinetd`**) lauscht stellvertretend auf vielen Ports gleichzeitig und startet den eigentlichen Dienst **erst bei eingehender Anfrage** (*On-Demand*). *Nachteil:* Hohe Startlatenz – für stark frequentierte Dienste (wie Apache HTTP oder Datenbanken) laufen daher immer dedizierte Daemons.
